# Bee Home — revival brief

Working notes for rebuilding the Bee Home 3D visualiser / builder that used to live at
`beehome.design`. Sources: the files in this repo, third-party coverage of the launch
(May 2020), and — most usefully — the **archived front-end itself**, recovered from the
Wayback Machine into `docs/reference/`. See §7 for the inventory.

Because the original bundles were recovered, most of what follows is read directly off
the shipped code rather than inferred. Where something is still inference, it says so.

---

## 1. What the original was

SPACE10 (IKEA's now-closed research and design lab) released Bee Home on World Bee Day,
20 May 2020, as a free, CC BY 4.0 open-source design for solitary-bee hotels. The point
was less the bee hotel and more the distribution model: a parametric product you
configure in the browser, download as cutting files, and have fabricated at a local
makerspace or CNC shop.

Roles, per the repo README and `ReadMe.pdf`:

| Role | Who |
| --- | --- |
| Project owner | SPACE10 |
| Physical design | Tanita Klein |
| Grasshopper definition | ChipChop |
| Online parametric engine | ShapeDiver |
| Digital interface / identity | Bakken & Bæck |
| Photography | Irina Boersma |

### The original stack

Bakken & Bæck's write-up describes the chain as **Grasshopper → ShapeDiver → three.js**:

- The Grasshopper definition (`BEEHOME.gh`, in this repo) is the source of truth for
  geometry and for generating nested 2D cutting files.
- ShapeDiver hosted that definition as a cloud parametric service, so the website could
  request a configuration without running Rhino.
- three.js rendered the result in the browser, with **AR viewing** as an explicit goal —
  "view the model from all angles, both in 3D and augmented reality".

That's the piece worth rethinking on a revival: ShapeDiver is a paid hosted dependency,
and the whole configuration space here is small and enumerable (see §3). A modern rebuild
can ship the storey library as static glTF and do the assembly maths client-side, keeping
Grasshopper only for regenerating the source geometry and the CNC nesting.

## 2. What's already in this repo (the useful part)

`BEEHOME GEOMETRIES.3dm` contains two layers that are literally the original web assets.
A `REFERENCE` text object in the file names them:

> `WEBSITE 3D geometries (.obj export)`

So the original viewer was fed OBJ exports of these layers. Contents:

**`WEBSITE - Model`** — 40 solids: 32 in two vertical stacks of 16, plus 8 guide solids.
The recovered front-end (§7) tells us exactly what these became. Its model manifest lists,
for every letter A–P, **two** OBJ files — `/models/X_default.obj` and
`/models/X_holes.obj` — plus `ground.obj`, `legs.obj` and `spike.obj`. That is 32 + 3,
and it lines up with the two stacks of 16:

- **Stack at x ≈ 8600** — 16 uniform bodies, all **120 × 160 mm**, heights 30–36 mm.
- **Stack at x ≈ 8000** — 16 bodies, same heights, varying footprints (120, 132, 138,
  144 mm wide; 160–192 mm deep — i.e. some have overhangs).

Which stack is `_default` and which is `_holes` is **not settled**. The obvious reading —
holes are subtractive, so they'd share a bounding box — is contradicted by the differing
footprints, so the pair is more likely "body shell" and "separately-drawn cavity
geometry" rather than "solid" and "solid minus holes". This needs ten minutes in Rhino to
confirm, and it matters, because it determines whether the viewer draws one mesh or two
per storey.

> **Correction to an earlier draft of this note:** I first read the two stacks as the
> `DEFAULT` vs `ROOF`/`FIXED` groups named in `ReadMe.pdf`. That was wrong — those three
> groups are a *Grasshopper/ShapeDiver-side* concern (see the `0`/`1`/`2` suffixes in §3),
> and are a different axis from the viewer's default/holes OBJ pair.

**`WEBSITE - Guides`** — the three mounting options, labelled in the file, matching
`ground.obj` / `legs.obj` / `spike.obj` in the manifest:

| Label | Geometry | Maps to |
| --- | --- | --- |
| `Base` | 140 × 160 × 30 mm plate (×3) | `ground` — the plinth under the stack |
| `Legs` | 15 × 30 × 50 mm × 4 | position `01` Standing |
| `Spike` | 30 × 30 × 200 mm | position `02` Grounded |

The manifest distinguishes `ground` from `ground_standing` (both pointing at
`ground.obj`), which is why there are three plates.

A dump of every object with its bounding box is in `docs/website-geometry.json`,
regenerated by `tools/extract_website_geometry.py`.

**Caveat:** the 3dm stores these as Breps/Extrusions with no render meshes attached, so
`rhino3dm` alone can read dimensions but cannot tessellate them. Producing glTF needs
either Rhino/`Rhino.Compute`, or a headless mesher. The stack ordering (which body is A,
which is P) is inferred from vertical position and still needs a visual check against the
`REFERENCE` layer's `A . B. C. … P` label row.

Also present: `BEEHOME Components.3dm` (63 objects — the spine/key joinery parts),
`Production Stock.3dm` (stock sheet + work area for nesting), and `PLUGINS.zip`
(the Grasshopper plugins the definition depends on).

## 3. The configuration model — fully specified

This is the best find in the repo. `ReadMe.pdf` documents the complete parameter space as
a **Bee Home ID** string, which is what the website generated and handed to Grasshopper.

```
XX  xxxx   xxxx
│   │      └── storeys, in letters (A–P), bottom-to-top
│   └───────── height in mm
└───────────── position
```

| Position | Code | Height field |
| --- | --- | --- |
| Standing (on legs) | `01` | digits, e.g. `200` |
| Grounded (on spike) | `02` | digits, e.g. `1150` |
| Fixed (wall/rooftop mounted) | `03` | *n/a — omitted* |

Examples from the PDF:

- `01196APPM` — standing, 196 mm tall, 4 storeys A-P-P-M
- `03NOPJNO` — fixed, 6 storeys
- `021000AB` — grounded, 1000 mm tall, 2 storeys

### Storey sets

Storeys ship as sets of 1–3 that can also be split apart:
`A+B`, `C`, `D+E+F`, `G+H`, `I+J`, `K+L`, `M`, `N+O+P`.

### Stacking rules — settled

Cavity positions mean not every storey can sit on every other. `ReadMe.pdf` states the
rules twice, and the two versions **disagree** (body text vs. diagram caption, differing
on D, E, K, L and M). That ambiguity is now resolved: the shipped site carried the
authoritative table as an embedded JSON blob, recovered verbatim to
`docs/reference/extracted/storey-rules.json`.

Note the framing is inverted from the PDF's. The site expresses it as
**`disallowedNextLetters`** — what may not be placed *above* a given block — and it keys
on both individual letters and whole sets:

| Block | Disallowed above it |
| --- | --- |
| `A+B` | — |
| `D+E+F` | A, B, C, I, J, K, L, N, O, P |
| `G+H` | A, B, C, I, J, K, L, N, O, P |
| `I+J` | E |
| `K+L` | — |
| `N+O+P` | K, L |
| `A` | E, K, L |
| `B` | — |
| `C` | — |
| `D` | A, B, C, I, J, K, L, N, O, P |
| `E` | A, B, C, I, J, K, L, N, O, P |
| `F` | A, B, C, I, J, K, L, N, O, P |
| `G` | A, B, C, D, E, I, J, K, L, N, O, P |
| `H` | A, B, C, E, I, J, K, L, N, O, P |
| `I` | E, K, L |
| `J` | E |
| `K` | — |
| `L` | — |
| `M` | E |
| `N` | K, L, M |
| `O` | K, L, M |
| `P` | K, L |

Use the JSON, not this table — it's the shipped artefact, and it's already in the shape a
validator wants.

### The export string

The site's `floorsExportString(floors, position)` is the bridge to Grasshopper, and it is
worth copying exactly:

- Prefix the list with `BASE_STANDING`, `BASE_GROUNDED` or `BASE_FIXED`.
- Suffix every letter with a variant digit: `0` by default, so `A` → `A0`.
- The **topmost** storey always gets `2` instead — the roof variant.
- For `BASE_FIXED` only, the storey *below* the top gets `1`.
- Upper-case, join with commas.

So a standing 4-storey `A,P,P,M` exports as `BASE_STANDING,A0,P0,P0,M2`. Those `0`/`1`/`2`
suffixes are the `DEFAULT` / `FIXED` / `ROOF` geometry groups that `ReadMe.pdf` names —
a ShapeDiver-side concern, separate from the viewer's default/holes mesh pair.

### Why this matters for the rebuild

The whole space is: 3 positions × a height integer × a variable-length word over a
16-letter alphabet with adjacency constraints. That is small, local, and needs no cloud
parametric service. A revived builder can:

1. Load 16 (or 32, with variants) storey meshes once.
2. Stack them by translating along Z using the per-storey heights already tabulated.
3. Validate adjacency client-side from the rules above.
4. Emit the same Bee Home ID string — which keeps the existing Grasshopper file working
   as the fabrication back end, unchanged. **The ID is the compatibility contract with
   the original project; keep it byte-identical.**

## 4. Visual direction

### The physical object

Hardwood throughout — the original deliberately left species open so people used local
timber, typically CNC-cut sheet at 6 mm (the layer names in the 3dm are all
`T6MM`, with one `T5MM` pocket set). Assembly is a **spine-and-key** system inspired by
Japanese wood joinery: storeys thread onto a vertical spine and lock together, so the
whole thing can be dismantled for cleaning without glue or fasteners. The look is
unfinished pale timber, visible end grain, stacked horizontal bands with a rhythm of
drilled cavities of varying diameters, capped by an overhanging roof storey.

The one photo in this repo — `SPACE10-Bee_Home_Makery_Process-Web-Photo_by_Irina_Boersma_04.jpg`,
from the Makery process shoot — is the best in-repo reference for material and finish.

### The digital identity — recovered

**Typography.** Two faces, both recovered:

| File | What it is |
| --- | --- |
| `S10Beehome-Display.woff2` | **The custom display face.** 16 KB — small enough that it's almost certainly a display cut with a limited character set. This is the mark Bakken & Bæck describe as drawn from "the shape of bees and the rounded form of their nests and tunnels". Committed to `docs/reference/fonts/`. |
| `markers.woff2` | A small icon/symbol font (7 KB) used for UI markers. Committed. |
| `NeueHaasUnicaW1G-Regular.woff/woff2` | The body face — **Neue Haas Unica**, Linotype/Monotype, licensed via MyFonts in May 2020. **Not committed** — see §7. |

**Palette**, counted off the shipped CSS-in-JS. The striking thing is what isn't there:
no yellow, no black, no honey. It's a warm bone-and-charcoal neutral base with a single
cool accent — consistent with the "bees are red-blind and UV/blue-shifted" research the
studio described.

| Hex | Role |
| --- | --- |
| `#E9E9E1` | Bone / warm off-white — the dominant background, by a wide margin |
| `#2A2920` | Warm near-black — text, and the 3D viewer's clear colour |
| `#D3D3CE` | Light warm grey — dividers, disabled states |
| `#7D7D73` | Mid warm grey — secondary text |
| `#898179` | Warmer mid grey |
| `#F1D6BA` | **Pale wood/sand — the timber base colour in the 3D material** |
| `#A5B7E6` | Periwinkle — the one cool accent |

(`#663399` appears in the manifest but it's Gatsby's default `rebeccapurple` from the
starter template, left unchanged. Ignore it.)

**The 3D material**, read straight off the AR export code — this is the recipe for making
a revived viewer look like the original:

- Base colour `#F1D6BA` with `WoodPlywood001_COL_2K.jpg` as the colour map,
  `repeat(2, 2)`, `RepeatWrapping` both axes.
- An `aomap.png`, and `birch_normal.png` / `birch_specular.png` alongside it.
- Faces are split across **three material slots by normal direction** — one for faces with
  `normal.y === 0`, another for `normal.x !== 0`, the rest default. That's the end-grain
  trick: plywood edges read differently from face grain, and this is how they got it
  cheaply without UV-unwrapping.
- Scene: **no grid, no ground plane, shadows off**, clear colour `#2A2920`, camera
  rotation speed 2. A floating object on a dark warm field — not a room, not a garden.
- Model units are mm; the AR export scales by `0.001` to get metres.

All four textures are in `docs/reference/textures/`.

### The interface

Site structure, from the recovered routes: three top-level sections — **Design**,
**Learn**, **Explore** — plus `/fablab`, `/ar`, and internal `/admin`, `/jsondump`,
`/firebase`, `/shapediver` pages.

The landing copy, verbatim:

> **Design a Bee Home and help restore the relationship between people and the planet.**
> Design your Bee Home · Learn about Bee Home · Explore the Community · #BeeHome

Footer: *"A SPACE10 project in collaboration with Tanita Klein and Bakken & Bæck."*

The flow, from coverage and consistent with the recovered code:

1. Choose **where it goes** — rooftop, backyard/garden, or balcony, mapping onto the three
   mounting positions.
2. Choose **height**, **number of storeys**, and which storey letters (cavity patterns),
   with invalid stacks blocked live by the rules in §3.
3. Preview in **3D from all angles**, and in **AR** in your actual garden.
4. **Download** a zip, assembled client-side with JSZip, containing `Bee Home CNC.dxf`,
   the assembly guide PDF, and a PNG snapshot of your design.

Repeated framing in the coverage: "fun, intuitive, and easy enough to do in a matter of
minutes." That's the bar — a toy, not a CAD tool.

Landing imagery is in `docs/reference/images/` — `LandingHero.jpg`, `LandingExplore.jpg`,
`LandingLearn.jpg`, each with a matching blur-up placeholder SVG.

### The "Explore the Community" half

Worth noting because it doubles the project's scope: designs were persisted to
**Firebase**, and `/explore` showed other people's Bee Homes. The `/admin` and `/jsondump`
routes exist to moderate and export that. A revival can legitimately skip this and ship
the configurator alone — but the community gallery is why the original felt alive, and
it's the part that needs a back end.

## 5. Gaps and next steps

What's actually still missing, now that the front-end is recovered:

- **The `/models/*.obj` meshes were never archived.** The Wayback crawler picked up the
  HTML, JS, fonts, textures and images, but not the 32 OBJ files. They have to be
  regenerated from the `WEBSITE - Model` layer — which is fine, that layer *is* their
  source, but it needs a meshing pass through Rhino or Rhino.Compute.
- **No screenshot of the configurator itself.** Only the landing page and its three hero
  images were captured. Reconstructing the actual builder UI would mean serving the
  recovered bundle locally and stubbing the dead ShapeDiver/Firebase calls — possible,
  since everything else is present, but a project in itself.
- **Which stack is `_default` vs `_holes`** (§2) — one Rhino session settles it.
- **Height semantics**: whether the `height in mm` field is total height or the elevation
  of the stack above ground isn't stated. The `01196APPM` example (196 mm, 4 storeys ×
  ~33 mm ≈ 132 mm of storeys) suggests *total*, with legs making up the difference.
- **Dead third-party dependencies.** The ShapeDiver model ticket in the bundle points at
  `eu-central-1` and is certainly expired; the AR pipeline posted to
  `gltf-from-usdc.herokuapp.com`, a free-tier Heroku app that no longer exists. Neither
  needs replacing like-for-like — see below.

Suggested build order:

1. Mesh the `WEBSITE - Model` layer to glTF (Rhino or Rhino.Compute, once); commit the 32
   storey meshes plus ground/legs/spike as static assets.
2. Port the Bee Home ID grammar and `storey-rules.json` to a small, tested pure module.
3. three.js viewer: stack by translating along Z, orbit, three mounting modes, the
   material recipe from §4 with the recovered textures.
4. `<model-viewer>` for AR — it handles both USDZ and Scene Viewer natively, replacing the
   whole dead Heroku round-trip with a tag.
5. Only then the export path. Keeping Grasshopper as an offline step is legitimate: the
   `.gh` file in this repo already accepts the ID and produces the cutting files, so
   shipping the configurator without a DXF back end still leaves a complete pipeline.

Dropping ShapeDiver and the Heroku converter removes both of the original's paid/hosted
runtime dependencies. What's left is static assets and client-side maths — which is the
main reason a revival is tractable at all.

## 6. Recovered archive — `docs/reference/`

Pulled from the Wayback Machine (142 unique 200-status URLs for `beehome.design`,
captures spanning 2020-05-20 to 2023). Downloaded with the `id_` modifier so the files are
the raw originals, not Wayback-rewritten copies. `tools/fetch_archive.py` reproduces it.

| Directory | Contents |
| --- | --- |
| `pages/` | `index.html`, `design.html`, `about.html`, `community.html`, plus Gatsby `page-data` JSON |
| `js/` | 24 bundles, 8.5 MB — the complete front-end, including the 5.8 MB main configurator chunk |
| `fonts/` | `S10Beehome-Display.woff2`, `markers.woff2` (see licensing note below) |
| `textures/` | `WoodPlywood001_COL_2K.jpg`, `aomap.png`, `birch_normal.png`, `birch_specular.png` |
| `images/` | Landing hero/explore/learn JPGs + placeholder SVGs, full favicon set, social card |
| `assets/` | **`Bee Home Assembly & Maintenance Guide.pdf`** (the real one, 564 KB), manifests, `robots.txt`, `font-license.css` |
| `extracted/` | `storey-rules.json` and `model-manifest.json`, lifted out of the main bundle |

### The site was Gatsby

Gatsby + TypeScript (`component---src-pages-*.tsx` chunk names), emotion for styling,
Firebase for persistence and remote config, JSZip for client-side packaging, ShapeDiver's
Parametric Viewer v2.19.2 for the parametric back end, three.js for the viewer, and a
Heroku microservice for USDZ/GLB conversion. The `.js.map` references in the bundles are
dead — sourcemaps were not archived — so the code is readable but minified.

### Redactions

Two Mapbox `pk.` client tokens were baked into the main bundle — the `/fablab` page used
Mapbox to plot local makerspaces. They have been replaced with `REDACTED_MAPBOX_TOKEN`.
They were publishable rather than secret keys, and are from a site that has been offline
for years, but they are someone else's credential and there is no reason to republish
them. A revival needs its own token for any map feature.

### Licensing note — read before publishing anything

- **Neue Haas Unica is not redistributable.** The MyFonts license notice shipped with it
  (`assets/font-license.css`) states plainly: *"All other parties are explicitly
  restricted from using the Licensed Webfont(s)."* It's therefore `.gitignore`d and **not
  committed** — it exists only in this container. Any revival needs its own license, or a
  substitute (Inter and Neue Haas Grotesk-alikes get close).
- `S10Beehome-Display.woff2` and `markers.woff2` are committed as project artefacts of a
  CC BY 4.0 project, but note the CC BY 4.0 grant in the README covers *the design*, and
  doesn't explicitly name the typeface. If this ever goes public-facing, confirm rather
  than assume.
- Everything else — the design, the geometry, the guide — is CC BY 4.0 with attribution to
  SPACE10, Bakken & Bæck and Tanita Klein.
